Q1

Can we trust any of this, and where does it break?

  1. Profiled every column of all three files
  2. Counted empties, placeholders and unusable values
  3. Cut the counts by city, month, category and payment
  4. Checked which problems travel together on the same rows.

Result: 22 columns profiled; quality datamart 6103 rows.

Decision: Fit-to-report judgement per business area; worst areas quarantined, not silently dropped. Alternative: A single global quality score. Effect: Global score would hide city/month concentration.

Evidence: src/quality_checks.py ·

Q2

We are paying commission on orders that never happened.

  1. Separated exact copies (D01), conflicting repeats (D02), same-person customers (D03) and product repeats (D04) with named rules
  2. Reconciled counts three ways: by id, by line, by customer/product/date
  3. Priced commission before and after each rule.

Result: 6103 rows in, 6000 clean; commission leakage from commission_datamart.

Decision: Dedup order D01>D03-remap>D02>D05, D06 flag-only. Alternative: Delete every repeated id outright. Effect: Blanket delete would remove genuine repeat purchases.

Evidence: src/deduplication.py · reports/deduplication_report.md

Q3

Which of these orders can I put my name to?

  1. Twelve checks (R01-R12) combining customer, product, price, date, quantity and status fields
  2. Counted what each check removes by city, month and category
  3. Kept a strict and a lenient population and compared them.

Result: Lenient 522 rows Rs 455,160.75; strict 115 rows Rs 79,738.50; rejected 5478.

Decision: Lenient (FAIL excluded, WARNING kept) feeds every Q4 answer. Alternative: Strict (warnings excluded) or legacy R01-R11. Effect: Strict drops 407 valid delivered rows; legacy keeps R12 failures.

Evidence: src/validation_rules.py + src/trusted.py · docs/waterfall.md

Q4

What do I tell the leadership team?

  1. Answered from trusted delivered orders only, one line value, cuts by month, city, category, payment and tenure
  2. Every total reconciles across cuts
  3. Ties flagged, impossible delivery days set aside.

Result: See Leadership answers section (computed marts).

Decision: Delivered-only revenue; DENSE_RANK top lists; city p95 for delivery. Alternative: All-status revenue; ROW_NUMBER tops; global p95. Effect: All-status inflates revenue with cancelled value; ROW_NUMBER hides ties.

Evidence: src/questions/seg6_leadership.py · reports/executive_report.md

Q5

I need this every Monday, written for people who will not read a table.

  1. Five marts at stated grains, refreshable from new files
  2. Model input is aggregated JSON only (PII asserted out)
  3. Every drafted figure is verified against a mart; runs and prompts are recorded.

Result: 5 marts; verifier tolerance 0.01; temperature 0.

Q1 · Rows per extract vs rows loaded pass

Method: `load_raw` parses every file with `csv.reader` and returns `(header, rows)`; `write_manifest` records `rows_in_file` and `rows_loaded` from that same pass, so the comparison is like-for-like per table.

Answer: No data row is dropped — the only filter removes fully blank lines, and none exist; the header is validated, not counted as data. The difference is 0 for all three extracts, and the manifest keeps both numbers so a future drop cannot go unnoticed.

Code: src/data_loader.py::load_raw · SQL: sql/questions/seg1_q1.sql · parity: yes

Q2 · Odd column names kept verbatim pass

Method: `load_raw` compares each file header to `EXPECTED_HEADERS[table]` and raises `ValueError` on mismatch; `write_manifest` stores the header verbatim for audit.

Answer: Column names are kept exactly as the extract writes them — no rename at load. A mismatch is fail-fast, never a silent mapping, so if a source renames a column the pipeline stops instead of guessing at the data.

Code: src/data_loader.py::EXPECTED_HEADERS · SQL: sql/questions/seg1_q2.sql · parity: yes

Q3 · Numeric-looking text columns pass

Method: The loader keeps every cell as text (csv module, list-of-dicts; `dtype=str, keep_default_na=False` when profiling), so no type inference happens at load; a typed read was compared column-by-column on the raw forms to list where inference would disagree.

Answer: Text is the preservation layer and coercion happens only in the normalisation helpers (`parse_float`, `parse_int`, `parse_date`, `parse_discount_frac`), so leading zeros, currency symbols, '%' and mixed date formats can never be mangled by dtype guessing. Disagreeing columns (a naive typed read would change them): orders — `order_id` (leading zeros `O00007`), `customer_id`/`product_id` (case/dash/space variants), `order_date` (mixed formats), `quantity` (`-2`, `''`, `2.5`), `unit_price_paid` (rupee-symbol forms, `NA`), `discount` (`10%`, `15`, `20 percent`, `NA`), `delivery_days`, `payment_mode`, `order_status`; customers — `customer_id`, `phone` (111 values start with `0`), `signup_date`; products — `product_id`, `unit_price` (`₹60`, `1,200`, `NA`), `stock_qty` (`NA`).

Code: src/data_loader.py · SQL: sql/questions/seg1_q3.sql · parity: yes

Q4 · Short/long order rows pass

Method: `row_length_audit` counts fields per parsed row and the manifest stores the distribution per table; a row broken by quoting would show a length different from its header.

Answer: No short or long rows exist — the standard CSV quoting rules inside `csv.reader` keep every logical row intact. The audit is a permanent guard: a malformed row cannot pass unnoticed in future loads.

Code: src/data_loader.py::row_length_audit · SQL: n/a · parity: no

Q5 · Leading zeros and spaces in ids pass

Method: Id values carrying spaces, lower case or dashes are counted per column; `norm_id` (strip, UPPER, remove spaces/dashes) shows the canonical form. One example per class demonstrates preservation at load and canonicalisation at join time.

Answer: Raw ids stay verbatim in the extracts (audit trail) and joins use `norm_id` — variants like `C-0176` and `c0010` resolve without editing the source. Leading zeros survive because values are text; nothing is integerised.

Code: src/data_loader.py · SQL: sql/questions/seg1_q5.sql · parity: yes

Q6 · Dates changed on load pass

Method: `parse_date` tries the ordered 8-format list and then an ISO fallback; counts compare raw strings against their parsed ISO form to separate changed values from unparseable ones.

Answer: Day-first conventions are tried before month-first (`%d/%m/%Y` precedes `%m/%d/%Y`), so ambiguous strings follow the Indian convention — raw `01/11/2026` is read day-first as 1 Nov 2026 (visible in `quality_datamart` row O00004). Unparseable dates are quarantined, never guessed.

Code: src/normalise.py::parse_date · SQL: sql/questions/seg1_q6.sql · parity: yes

Q7 · File encodings pass

Method: `detect_encoding` checks a UTF-8 BOM, then strict UTF-8, falling back to cp1252; a byte-level scan lists every non-ASCII character per file, and a misread test decodes bytes as cp1252.

Answer: UTF-8 is tried before cp1252, so the rupee sign decodes correctly; cp1252 stays only as a legacy fallback. No accent misreads are possible here (none exist), and `parse_float` defensively strips the rupee sign and commas so decoded symbol forms still parse.

Code: src/data_loader.py::detect_encoding · SQL: sql/questions/seg1_q7.sql · parity: yes

Q8 · Quotes inside notes pass

Method: `csv.reader` handles quoting; the check counts notes containing commas or double quotes and re-audits row lengths — a quoting failure shows up as a wrong field count.

Answer: Embedded commas and quotes are handled by standard CSV quoting (`""` escaping) rather than custom splitting, and the row-length audit proves no affected row misaligned.

Code: src/data_loader.py::load_raw · SQL: sql/questions/seg1_q8.sql · parity: yes

Q9 · Loading the same file twice pass

Method: `load_raw` was run twice per extract and `sha256_of` twice per file in one session; row counts and hashes were compared (live demonstration, not a by-construction claim).

Answer: Extracts are immutable, content-addressed inputs: the manifest pins file, SHA-256, encoding, header and row counts, and reloading is idempotent — same bytes give same rows and same hash. Reruns therefore reproduce identical state; there is no sampling or randomness anywhere in loading.

Code: src/data_loader.py::load_raw · SQL: n/a · parity: no

Q10 · Empty vs placeholder cells per customer column pass
